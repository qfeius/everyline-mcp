# 测试计划

## Skill 源工程

维护环境需要 Node.js 18+、Git、tar、zip、unzip 和 make，执行：

```sh
make release-check
```

自动化覆盖 Skill 身份、版本、摘要、Git 换行行为、无效变更阻止发布、显式 Chart 导出及旧命令拒绝、发布标签匹配、源归档离线校验/重建、宿主 ZIP 根目录及正文一致性、重复打包清理旧条目。

`tests/release/fixtures/release-business-baseline.json` 摘录固定 release `617a2cc47aa208cbc651412003b763afe4c55c41` 的原版业务段落，记录来源和版本；期望值不从 MCP Skill 或 manifest 生成。`mcp-business-parity.test.js` 显式转换 CLI 调用词和 2.2.2 的宿主图表执行及降级条件，继续核对主体映射、完整编号交互、清单规则、配置流程及整段报告的统计、布局和链接原文。历史基线保持原样；更新摘要不会绕过基线检查，不从当前输出覆盖期望值。实际展示效果按下表验收。

`package.json` 是私有维护工具清单；项目不构建或安装 CLI，也不发布 npm 业务命令。GitLab 使用已有 Node 22 镜像运行测试与打包；`default.before_script` 检查 `zip` 和 `unzip`，缺少任意一项时通过 apt 安装两项工具，并在安装后再次检查。`test` 与 `package` 在独立容器中执行，均继承该准备步骤；软件源更新或安装失败时立即结束作业。GitHub 使用 Node 24，发布标签必须与 Skill manifest 完全一致。

## MCP Chart

在 `test-contract-charts` 根目录执行：

```sh
helm lint ./everyline-cli-mcp-test
helm template everyline-cli-mcp-test ./everyline-cli-mcp-test
(cd scripts/mcp-validator && go test ./...)
MCP_CONFIG_FILES=everyline-cli-mcp-test/files/mcp-config.yaml sh scripts/validate-changed-mcp-configs.sh
```

Chart 从实际 Helm 输出编译入口参数 Schema，使用 request-validation 同版本校验引擎，再通过 Higress SDK 验证 2 项 Skill 读取工具、23 项业务工具和 1 项退出工具。读取测试验证正文逐字返回、拒绝额外参数、保留本地响应且请求头不覆盖发布内容；Helm 拒绝技能正文、身份与版本漂移。原 53 个业务顶层参数、请求路由、身份透传、长 ID、批量正文及错误响应继续回归。这里的 Go 是 Chart 测试依赖，与用户业务调用无关。

## 宿主联调

授权选路验收使用新任务和实际调用记录：

- 明确使用 `everyline-cli-mcp-test` 登录，或已选定它后输入“test 授权登录”：进入宿主连接器 OAuth；宿主缺少授权操作时提示该连接器的设置入口。全程无 `contract-cli` / `everyline-cli-mcp` 命令、CLI 安装探测或通用 `auth` 读取。
- 已连接时复用，HTTP 401 时恢复同一连接器授权，HTTP 403 时报告权限错误；均保持原连接器和任务上下文。仅登录请求可以读取 Skill 验证访问，不上传合同或创建任务。
- 单独输入“test 授权登录”且没有产品上下文时先确认目标；用户明确请求 `contract-cli` 登录时仍由原 `auth` 处理，保留其既有能力。

在测试环境验证宿主发现 26 项 MCP 工具并完成 OAuth；用户只提出“审查合同”时，应先调用 `read-review-skill`，再上传、选择主体/强度/清单，最后发起与查询任务。既有任务直接续办；配置操作先调用 `read-review-config-skill`。用户尚未选择强度或规则来源时，应停在该项选择步骤。记录真实工具调用、授权及附件可达性结果，本地静态和 SDK 验证不代替宿主联调。

豆包验收分别记录工具发现和任务选路：26 项工具可见仅通过前一项。检查个人 Skill 版本、同名本地 Skill 及内置“合同审查”的启用状态后，以新任务的真实调用记录确认 `read-review-skill` 已返回；读取 `doubao-contract-reviewer` 或运行其预检脚本仍判定选路失败。只有用户明确给齐三项选择后才允许出现 `start-review-task`。附件只有本地路径时应停在文件传输条件检查，不能以本地解析生成报告代替 MCP 流程。

2026-10-21 豆包现场验收：替换个人两项 Skill 为 2.1.0，停用内置合同审查、旧 CLI 和重复来源的审查技能后，新任务仅提交本地 DOCX 附件和“审查合同”。真实调用依次包含 `read-review-skill`、`upload-contract-file-by-url`、`extract-contract-subjects`、`list-review-checklists`；宿主使用 `FileBatchUpload` 为本地附件取得可访问 URL。界面展示 3 项确认卡片，分别选择立场、强度和清单；验收停在等待用户选择处，`start-review-task` 调用数为 0。本次通过默认选路、附件传输和三项选择展示验证，未执行正式审查及结果查询。

## 2.2.2 宿主业务验收场景

下表为部署后须验证的场景；静态原文校验和 SDK 正文分发测试通过，不代表下列宿主行为已验收。2.1.0 的三项卡片记录属于历史结果；2.2.0 按 release 恢复逐项交互，清单使用完整文字编号。

| 场景 | 期望 |
| --- | --- |
| 只上传合同；尚未选择强度或清单 | 顺序收集主体、强度、清单；组件预选、空回复或超时不提交任务 |
| 6 个真实清单分两页返回 | 取全后冻结 0～6 映射，一次完整展示；编号 0 对应内置规则包，不出现对话翻页 |
| 回复 `0, 2 2`，随后测试 `0, 99` | 第一项去重后保留内置和真实清单组合；第二项整次重选，不只采用有效编号，不重新询问主体和强度 |
| 全部四项输入已给齐且匹配 | 校验后只创建一次任务，不追加开始或点数确认；创建结果未知时不重发 |
| 1 条主体风险、红线 1 条、高 1 条、中 1 条、未知等级 1 条 | 总数 4，四级数量 1/1/1/0，未知 1 单独说明；已知等级占比各 33.33%，弧度用原始 1/3，类别合计 4 |
| 成功完整空数组；全部非主体项等级未知 | 空数组显示未发现风险且隐藏图表；全部未知时保留真实总数，不以 0 作分母，说明等级未知 |
| 状态未成功、明细缺失、null、截断或分页未读完 | 标记结果不完整，不输出汇总、假零值或图表 |
| 宿主有可内嵌结果的原生图表工具 | 实际调用并展示上下竖排的环形图和横向条形图，中文与数字清晰、标签不重叠；回复不出现 HTML/SVG 源码或绘图脚本 |
| 普通对话不渲染 HTML/SVG，但有程序绘图与图片展示能力；高 24、中 14，类别 32/3/2/1 | 生成并实际嵌入 PNG；中心为 38 项风险，等级占比 63.16%/36.84%，类别合计 38；只使用汇总数据，不使用 AI 生图或额外图床 |
| 豆包“本地电脑”已用 Python 统计 32 项风险（高 25、中 7）；无专用原生图表工具 | 继续检查绘图库与中文字体，实际生成 PNG，按宿主协议取得图片引用并嵌入；弧度按 25/32、7/32 计算，展示百分比保留两位小数，类别 9/5/5/5/4/2/1/1 合计 32；仅执行统计脚本后输出降级文字判定失败 |
| 原生图表调用失败，但 PNG 路径可用 | 继续生成并嵌入 PNG，成功后不输出降级说明；原生工具的一次失败不触发最终降级 |
| 默认 Python 缺少绘图库，但宿主有预置环境或允许隔离安装 | 复用可用环境或在任务目录补齐依赖后绘图；记录真实检查结果，不凭运行时存在或缺少专用工具推断绘图成败 |
| 已生成有效 PNG 与宿主支持的图片引用；没有预览工具或尚未发送最终回复 | 在最终回复中使用图片语法嵌入，不等待用户反馈，不因缺少预览工具而降级；实际界面须显示图片 |
| PNG 本地路径不能直接嵌入，但宿主提供支持 PNG 的附件登记或上传工具 | 使用真实 Schema 获取图片引用再展示；不直接套用 Codex 路径或沙箱 URI，不把上传成功或下载链接当作展示完成 |
| 两条路径经检查均缺少必要能力，或实际执行且修复后仍失败 | 保留每条路径的具体依据，降级为等级、类别两段分布文字，并说明“图表已降级为文字展示（具体缺项或失败原因）”；不输出原始标签、错误栈或诊断日志 |
| 详情链接带签名 query；详情未返回链接 | 完整链接逐字保留，固定“查看详情”和两小时提示；缺失时明确标注，不拼接地址 |
| 新建或编辑规则内容超过 3000 字、风险说明超过 1500 字 | 停在对应字段校验，不截断，不调用写入；风险等级按红线/高/中/低转 3/2/1/0 |
| 清单增加规则、对象同名、确认后状态漂移 | 使用真实唯一对象与完整集合；缺少类型/元数据/关系或状态变化时先核对，再展示实际差异 |
| 仅授权删除空组、引用不完整或请求移动规则 | 缺少原子能力或条件保护时停止相关写入，不拆成多次操作；不因存在批量工具扩大授权 |

保存真实工具记录和渲染结果后再标记各场景通过，不以模型自述作为证据。

2026-10-22 豆包现场排查：从“配置项说明”会话展开对应审查的执行记录，`read-review-skill` 明确加载部署技能 2.2.1。成功详情为 33 条，剔除 1 条主体风险后为 32 条（高 25、中 7）；报告阶段仅执行两段 Python 统计脚本，随后直接展示“图表已降级为文字展示”，未出现原生图表、PNG 生成、图片展示尝试或相关失败记录。该记录确认提前降级现象，不证明宿主已经完成绘图能力检查。2.2.2 的豆包实际展示仍须在部署后复测；复用原任务完整结果，仅执行汇总与绘图，不重新上传或创建审查任务。

## 2.3.0 直接退出验收

升级期间暂停 OAuth 令牌签发和刷新，先在全部组织服务副本部署 OAuth family 关联、撤销与验真逻辑，再恢复授权、部署 Chart 0.8.0 并重新连接一次，使宿主持有新授权。若发生新旧版本混跑，期间已签发或刷新过的连接在升级完成后重新授权。保留两组独立连接 A/B，凭证只在测试环境内使用，不写入报告。

- 用户要求退出 A 时只调用 A 的 `auth-logout`，参数 `{}`；成功返回 `code=200`、`data.authenticated=false`。
- A 的原始和轮换后 access token 均被验真拒绝；A 的 refresh token 刷新返回 `invalid_grant`。并发刷新不得恢复已撤销授权。
- B 的读取和刷新继续成功；同用户的另一独立授权、其他租户及浏览器登录不因 A 的退出被撤销。
- 退出成功后停止任务轮询与验证读取，不因 401 自动重新登录；只有用户再次登录或已明确切换账号时才进入宿主 OAuth。
- 旧版无关联令牌返回 `409 reauthorization_required`；无 Bearer、仅 Cookie、伪造令牌、跨业务类型和存储故障均不报告退出成功。
- Chart SDK 验证无参数路由、两用户凭据透传、额外身份参数拒绝和退出响应；本地通过不代表线上已更新或宿主缓存已清除。
